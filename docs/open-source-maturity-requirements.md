# AI Quant Agent 成熟开源项目要求

> 定位：面向 A 股研究、回测与模拟交易的可复现开源平台。
>
> 本文将“成熟”定义为：用户可以安全安装和使用，贡献者可以稳定协作，维护者可以可控地发布，并且研究结论可以追溯与复现。它不表示项目适合无人值守实盘交易，也不构成投资建议。

## 1. 发布门槛

每个正式版本必须同时满足：

- 干净环境可通过 `uv sync` 安装，并可通过 `quant-agent --help` 验证入口。
- 所有自动化测试通过，且单元测试与常规集成测试不依赖网络、真实 API token 或本机已有数据。
- 版本号、`uv.lock`、依赖清单、README、CLI 帮助和 CHANGELOG 一致。
- 不存在已知的高危依赖漏洞、明文密钥、被忽略的 TLS 证书校验错误或路径遍历风险。
- 每项面向用户的行为均有文档、测试和变更记录。

## 2. 工程质量要求

### 2.1 可重复构建与测试

- 使用 `pyproject.toml` 作为唯一依赖与打包定义；所有运行时直接导入的第三方包必须被声明。
- 使用锁文件锁定可复现环境；支持 Python 3.10、3.11、3.12 的 CI 矩阵。
- 采用 Ruff（格式、lint、import）和静态类型检查；新增公共 API 必须有类型标注与文档字符串。
- 对关键路径设置覆盖率门槛：数据校验、风控、策略、订单/组合、报告持久化与 Web API。
- 测试分层：`unit` 完全离线，`integration` 使用 fixture/fake 数据源，`smoke` 才可访问外部数据源并以定时或手动方式执行。

### 2.2 兼容性与 API

- 为 CLI、配置项、报告 JSON、策略接口和数据源接口定义稳定契约。
- 不兼容变更必须进入 CHANGELOG，并遵循语义化版本：破坏性变更升主版本，新增功能升次版本，修复升补丁版本。
- 为配置提供 schema、默认值、合法范围和迁移说明；不应使用宽泛的 `MagicMock` 掩盖配置契约。

### 2.3 可观测性

- 日志采用结构化字段：请求/分析 ID、股票代码、数据源、数据时间、降级原因、策略版本和异常类型。
- 健康检查应暴露版本、数据源状态、缓存新鲜度和 LLM 可用性，但绝不暴露密钥或内部路径。
- 对数据源故障、订单拒绝、熔断触发、报告生成失败建立可机器读取的指标与告警出口。

## 3. 数据与研究可信度要求

- 每份分析和回测结果必须记录：数据源、抓取时间、可用最新交易日、复权/未复权状态、缓存年龄、缺失字段和降级路径。
- 样例数据、缓存数据、实时数据和合成数据必须有不可混淆的显式标识；示例数据不得被描述为实时行情。
- 回测必须明确其假设，并逐步覆盖：交易日历、停牌、涨跌停、最小交易单位、手续费、滑点、分红送配/复权、流动性约束、幸存者偏差和前视偏差。
- 策略运行产物必须保存策略版本、参数、随机种子、代码版本和依赖锁文件指纹，以便复跑。
- 默认输出应附带“仅供研究，不构成投资建议”的风险提示。

## 4. 安全与交易边界要求

- 默认模式仅允许研究、回测和模拟交易；任何实盘能力必须是独立的、显式启用的适配器。
- 实盘适配器必须具备人工确认、账户/单笔/日累计额度限制、交易时间校验、幂等订单 ID、撤单与 kill switch。
- 所有 HTTP 请求必须验证 TLS；不得通过关闭证书验证来规避网络问题。
- 机密信息只从环境变量或受控 secret store 读取，并在日志、异常、报告、Issue 模板中统一脱敏。
- Web 服务默认仅绑定 loopback；若支持远程监听，必须提供认证、CSRF/来源策略、速率限制和安全文档。
- 定期执行依赖漏洞扫描、密钥扫描和 CodeQL/静态安全检查；提供私密漏洞披露渠道。

## 5. 用户体验与文档要求

- README 在五分钟内说明项目定位、风险边界、安装、最小离线示例、最小联网示例、测试命令和卸载方式。
- 提供独立文档：架构、数据源与许可、配置参考、策略开发、回测方法、Web API、故障排查、升级迁移和安全说明。
- 示例命令必须可复制运行；示例输出标明数据性质与生成时间。
- CLI 的错误信息应给出可执行修复建议，不要求用户阅读源码。
- 发布版本需包含人类可读的 CHANGELOG 与升级说明。

## 6. 开源治理要求

- 根目录提供 `CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、`SUPPORT.md`、`CHANGELOG.md` 与项目路线图。
- 提供 Bug、功能、文档与安全问题模板，以及 Pull Request 模板和最小 Review 要求。
- 明确维护者、决策方式、支持范围、弃用政策和发布节奏；GitHub Discussions 用于开放讨论。
- 使用明确 SPDX 许可证标识；确认所有数据源、样例数据、图标和第三方代码的再分发许可。
- 新贡献必须通过 DCO 或 CLA 之一，并在 CI 中检查。

## 7. 发布与运营要求

- 主分支受保护：CI、代码审查和安全扫描通过后才能合并。
- 使用 GitHub Actions 自动执行测试、质量检查、构建、依赖审计和发布候选验证。
- 发布包到 PyPI 前使用 TestPyPI 验证安装，并为 release tag 生成可验证构件与 release notes。
- 维护 issue 分级（安全、回归、数据错误、文档、good first issue）和响应目标。
- 每个季度检查依赖、数据源可用性、许可证、路线图和安全基线。

## 8. 成熟度验收清单

### M1：可信 alpha

- [ ] 运行时依赖、版本、锁文件、README 一致。
- [ ] 全量测试通过；离线测试无网络访问。
- [ ] 风控、数据降级和模拟交易有明确测试覆盖。
- [ ] README 标注研究/模拟定位和投资风险。

### M2：可贡献 beta

- [ ] CI 覆盖支持的 Python 版本、lint、类型检查、测试与安全扫描。
- [ ] 贡献、安全、行为准则、支持和 Issue/PR 模板齐全。
- [ ] 有 CHANGELOG、版本策略和受保护主分支。
- [ ] 文档覆盖安装、配置、架构、数据、策略与故障排查。

### M3：稳定 1.0

- [ ] 公开 API/配置/报告 schema 已版本化并有迁移策略。
- [ ] 回测与报告完整记录数据和策略谱系，可在干净环境复现。
- [ ] 数据质量、交易边界与安全基线有自动化验证。
- [ ] 有固定发布节奏、维护者轮值/决策机制和可处理的社区反馈渠道。
